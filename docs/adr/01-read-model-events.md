# ADR-01. Денормализованная read-модель ЛК, обновляемая событиями

- Status: Accepted
- Date: 2026-07-30
- Deciders: Захаров Владислав (архитектор сервиса)

## Context
Личный кабинет показывает данные из нескольких сервисов: профиль, лояльность, рекомендации, внешние платёжный шлюз и служба доставки. Если собирать данные синхронно, задержки складываются, а отказ любого источника уронит весь кабинет.

Наши главные драйверы:
- D1: всплески нагрузок на чтение;
- D2: нестабильность смежных систем;
- D3: компромисс между скоростью отклика и актуальностью данных.

Внутри компании уже есть брокер, куда сервисы публикуют события об изменениях.

## Considered alternatives
1. **Параллельный опрос всех сервисов на каждый запрос.**
   Отклонено, так как время ответа будет равно времени ответа самого медленного источника, пики чтения ЛК транслируются на все доменные сервисы, а отказ любого соседа нужно обрабатывать в рантайме.
2. **Агрегация на клиенте (SPA ходит в каждый сервис сам).**
   Отклонено, так как много запросов с клиента, а фронт связан с каждым сервисом контрактами и каждому сервису нужно открывать публичный API.

## Decision
Агрегатор подписан на события по контракту, обновляет данные пользователя в MongoDB. BFF делает запрос в локальную базу данных. Всё, что можно получить событиями из своих доменов, хранится в read-модели. Синхронно ходим только туда, где события невозможны или бессмысленны (Auth, оплата, доставка).

## Consequences
**Плюсы:**
- Изоляция сбоев;
- Предсказуемый p99;
- Чтение масштабируется независимо;
- Graceful degradation для read-модели (при отказе показываем последнее состояние с временем обновления).

**Минусы:**
- Данные могут отставать на время доставки события через брокер;
- Нужна первичная загрузка;
- Требуется версионирование контрактов;
- Обработчик событий должен быть идемпотентным и устойчивым к нарушению порядка.
